## Architecture

- **Pattern:** Ports and adapters. The engine depends on interfaces. Harnesses, decider providers and git (`packages/engine/src/projects/git.ts`) are adapters behind them.
- **Module structure:** A layered vertical codebase in a Bun workspace. Packages sit in layers and import only downward. Inside a package, code is grouped by domain. `docs/steering/STRUCTURE.md` holds the layer map, what each package owns, and the rules. Two scripts check them on every commit and in CI: `scripts/check-layers.ts` (the layer map) and `scripts/check-verticals.ts` (the verticals of every workspace).
- **State management:** The server stores durable facts in libsql and appends every change to an event log. The UI derives status from facts and subscribes to the event log over SSE through TanStack Query.
- **Data flow:** UI → oRPC → engine → agents (harness or tool) → facts + event → SSE → UI. Everything runs in-process.
- **API contract:** The oRPC router in `packages/api` is the one source of the API. The web client, the OpenAPI document and the agent tools all come from it. Every procedure declares an input schema, an output schema and a one-line summary. An output schema checks a reply and never changes it (`packages/api/src/output.ts`).
- **One daemon runtime:** `packages/daemon` builds the daemon in one function (`createDaemon(env)`) and starts it in one boot sequence (`startDaemon()`). `bun run dev` (`apps/server/src/main.ts`), `nightshift serve` (`apps/server/src/features/cli/`) and the desktop app all call `startDaemon()`. Under `bun --hot` a reload calls it again: the lease, the documents and the listeners stay, the engine before lets go of its runs (`Engine.dispose`).
- **Devices:** `packages/devices` is this computer among other Devices and Hosts: Placement, Offers, the exchange of run history, the Links and pairing, this computer as a Host, and the work relay. The engine declares the ports it needs (`Peers`, and `DeviceDirectory` for the Device rows), and `createPeerEngine` wires them. The engine never imports `devices` and never queries its tables.
- **Notifications and the phone:** `packages/notifications` is the notifier. It reads the run log and decides whom to tell: a new Gate (keyed `runId:stepId`), a run that finished, a run that failed. The settings belong to the Person. Each channel (the in-app stream, Web Push, a desktop notification, Expo Push) sits behind a port. The phone app (`apps/mobile`) is a Person's client of a Host, not a Device. It shares its client logic with `apps/web` through `packages/client`. See `docs/research/mobile.md`.
- **Harness adapters:** `packages/agents` has one folder per harness in `src/harnesses/`: `claude-code/`, `codex/`, `opencode/`, `grok-build/`, and `acp/`. Each folder holds what is that harness's own: `facts.ts` (its entry of `HARNESS_CATALOG` in `@nightshift/flows`, plus the CLI, the take-over command and the skill folders: pure data), `record.ts` (the facts, the adapter's models and the install check), and `harness.ts` (a `HarnessSpec`, a TanStack adapter factory and a raw-message observer). `harnesses/registry.ts` and `harnesses/facts.ts` collect one record per harness. `harnesses/facts.ts` is the browser-safe `./harness-facts` entry. `src/session/adapter-session.ts` runs every Agent step as one TanStack AI session: it owns the sandbox in the worktree, the `chat()` call, the translator, the step report and the abort. `acp/` runs every agent that speaks the Agent Client Protocol through `acpCompatible`: GitHub Copilot, Gemini CLI, Cursor, and pi (through the `pi-acp` package, which `packages/agents` ships, see `acp/pi.ts`). Night Shift finds pi-acp when a pi session starts, not when it loads. The `nightshift` binary carries pi-acp inside and starts it as `nightshift pi-acp`. An agent without a model flag gets its model over ACP (`acp/session-config.ts`). A custom agent (`acp:<slug>` in a flow, `customAgents` in the settings) runs through the same path, with the command the person gave. `HARNESS_CATALOG` (`packages/flows/src/harnesses/`) holds what a person sees of each harness: label, initials, note, default model, the models the editor suggests, where the code goes, and the setting of its CLI path. It is browser-safe, so the web app reads it too. To add a harness, add its folder, one line in `registry.ts` and in `facts.ts`, and its name and its catalog entry in `@nightshift/flows` (`harnessNameSchema`, `HARNESS_CATALOG`).
- **Flow execution:** A flow is a JSON file in `.nightshift/flows/`, validated by a zod schema. Every Agent node runs as a harness session through a TanStack AI harness adapter and names a skill the harness already has. A Decision node picks one of its options: you (a Gate), a rule (a JSONata expression over the run's values), or a model whose pick is checked against the options.

## Key Constraints

- Store facts, never status. Derive status in a query or a view. Append an event for every change.
- The engine owns order, retries, loop limits, and gates. A model decision is a schema-validated label. Never let a model change the graph.
- Every loop in a flow has a maximum count. The validator refuses a flow with an unbounded loop.
- Every external I/O goes behind an interface in `packages/agents` or `packages/engine`. No `gh`, `git`, or harness call outside an adapter.
- Never delete a dirty worktree. Garbage collection skips any tree with uncommitted changes.
- Cap concurrent sessions. The cap is configuration, not a constant.
- A step runs in one repo. A cross-repo change is two steps.
- Put a tenant id on every row: `space_id`, the Space (a Better Auth organization). No query of a person crosses a Space. Only background work (the walk, recovery, the scheduler) reads every Space, and it writes each row with its own Space.
- Validate every flow file with the published zod schema before a run starts. A schema error stops the run.
- The app holds secrets in the OS keychain. Prefer the CLI's own login over a stored token.
- A step that runs unattended ends with a structured report. It never waits on a person mid-session.
- No PTY. A session is a structured event stream.

## Code Conventions

- **Naming:** PascalCase components and types, camelCase functions and variables, kebab-case file names.
- **File structure:** One workspace package per bounded context. Inside a package, group by feature, not by kind. Each vertical is a folder with an `index.ts` barrel as its only public surface (`src/features/<vertical>/` in apps, `src/<vertical>/` in packages). No `lib/`, `utils/` or `hooks/` buckets at the top of `src/`. See `docs/steering/STRUCTURE.md`.
- **Test files:** Colocated `*.test.ts` next to the module. Bun's test runner.
- **Imports:** Workspace packages by name (`@nightshift/db`). No relative imports across packages.
- **Formatting:** Biome. The pre-commit hook formats staged files.
- **Environment:** varlock schemas in `.env.schema`. Generated types, never `process.env` by hand.
- **Prose:** Durable docs follow the ASD-STE100 style of the WTF skills. Short sentences, active voice, one idea per sentence.

Receipts come about 15 minutes after a send: the channel reads them in chunks off the send path, and a `DeviceNotRegistered` makes the next send to that token answer `gone`, so the notifier forgets the target. | 2026-10-21 |
| The phone builds its client from `@nightshift/client`; screens get query options from the `host` vertical | `shared/api/transport.ts` is the phone's transport (`expo/fetch` with the body as an `ArrayBuffer`, flattened headers, the signal, `credentials: "omit"`, the session cookie from `authClient.getCookie()`). `features/host` makes `createApiClient` + `createQueryUtils` per Host and hands them out as `useHostQueries(createRunQueries)`, because the phone's client changes with the Host, unlike the web app's one `orpc`. The vertical is `host`, not `connection`: Connection is an MCP server in the glossary. | 2026-10-21 |
| The phone's Space is the session's active Space, remembered per Host | Runs and starting a flow are per Space, so Runs and Start have a Space picker in their header; it calls `spaces.switch` and keeps the choice in SecureStore under the Host's address. A new session starts in the personal Space, so after a sign-in the app switches back once. The inbox and the dashboard read every Space and need no picker. | 2026-10-21 |
| The Host code holds the https:// address only | The QR code in the web Settings (`qrcode.react`) is the address of the page when it is https://, else the first https:// Host address of this computer. A phone reaches a Host only at https://, and a code with a session or key would sign in whoever photographs it. The phone scans it with `expo-camera` and the person signs in as usual (two-factor code or backup code). | 2026-10-21 |
| The phone checks the person before it answers a Gate that is not a lock-screen Gate | `expo-local-authentication` asks for Face ID or a fingerprint and falls back to the passcode, so a phone without biometrics can still answer. A phone with no screen lock cannot answer such a Gate: the app says to set one up. A lock-screen Gate answered in the app needs no check. The rule is `answerCheck` in `apps/mobile/src/features/inbox/answer-check.ts`. | 2026-10-21 |
| The phone answers a lock-screen Gate from its notification, in the background, without an unlock | The `gate-decide` category has Approve and Reject with `opensAppToForeground: false` and `isAuthenticationRequired: false`: the flow author marked the Gate, so the answer needs neither the app nor Face ID. The response listener (and on Android the background task) first reads `gates.list` (a push is no proof: anyone with the phone's push token can send one) and sends only to an open Gate with `lockScreen` and one of its choices, else a local notification opens the Gate in the app. It calls `gates.resolve` with `via: "lock-screen"`, bound to the push's `runId` + `stepId` and the option (`approve` = `options[0]`, `reject` = `options[1]`); the Host refuses `via: "lock-screen"` for a Gate that is not marked; a closed Gate does nothing; the notification goes away. When the Host does not answer, a local notification says the answer was not sent and opens the Gate. To read the Host address and the session cookie on a locked phone, `shared/api/kept-store.ts` keeps them in SecureStore with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` (a write moves an older item to it; a restored backup does not carry the session to another phone). | 2026-10-22 |
| A lock-screen Gate has exactly two options, and the editor names what each button answers | An iOS category has fixed button titles, and a visible push shows without the app, so the buttons cannot carry the author's option names. They say Approve and Reject and answer by position. So flow validation refuses `lockScreen` on a Decision without exactly two options, and the editor says which option Approve and which Reject answers. A per-Gate category would need a Notification Service Extension. | 2026-10-22 |
| The phone registers its Expo push token at every start and asks for notifications only after the person taps | `features/push`: permission is asked from a card (Settings, the empty inbox), never at first launch. While signed in and allowed, the phone registers with `notifications.targets.register` (`kind: "expo"`, `Constants.deviceName`) with retries, and keeps the target id per Host in SecureStore. Signing out and "Remove this phone" remove that target first, so the Host stops sending and ends the session. Expo gives a token only with the EAS project id (`expo.extra.eas.projectId`, from `eas init`). | 2026-10-22 |
| In front, the phone shows no banner of its own; withdraws dismiss by key | `setNotificationHandler` hides the OS banner while the app is active; a Gate shows as a banner in the app unless the person is on the inbox or that Gate. A withdraw push (`{ withdraw: key }`) runs the background task (`expo-task-manager`, iOS background mode `remote-notification`), which dismisses every shown notification of that key; a `gate-closed` item of the in-app stream does the same, and each read of the open Gates dismisses the Gate notifications that no longer wait. Android has two channels, `gates` (high) and `runs` (default), and the Host's Expo channel names them. | 2026-10-22 |
| The phone's widget and lock-screen runs use `expo-widgets`, updated from the app, not by push | One maintained package gives the iOS widget and Live Activity and the Android widget and ongoing notification (`createCustomNotification`). Live Activity push goes to APNs with the app team's key, which the Expo push service does not send and a personal build does not have, so the app updates a followed run while it runs (every 5 s) and marks it out of date after 10 minutes without one. The widget and the lock screen show counts, flow names, step names and statuses only. "Step x of y" counts the flow's nodes that started, once each. | 2026-10-22 |
| The web app has a manifest, and Settings tells an iPhone or iPad to add it to the Home Screen | iOS gives Web Push only to a site on the Home Screen. `apps/web/public/manifest.webmanifest` (name Night Shift, `display: standalone`, `start_url: /inbox`) and `apple-touch-icon.png` make it one. The icons are `favicon.svg` in its dark colours on a solid square (`app-icon.svg`, PNGs drawn with `resvg`). In a browser tab on iOS, `needsHomeScreen()` makes the browser switch say how to add it. | 2026-10-22 |
| A push target is checked where it registers, and a phone's target ends with its session | `notifications.targets.register` takes only `web` and `expo`: a Web Push endpoint is an `https:` URL on FCM, Mozilla, Apple or Windows push (the Host posts to it, so any other address would let a Person make the Host call into its own network), and an Expo target needs a valid Expo push token. Only the daemon registers its `desktop` target, and the desktop channel shows only its owner's notifications. The Host forgets an `expo` target whose session is gone or expired, and a push token registered by one Person stops reaching any other Person. The phone takes only an `https://` Host address outside development. | 2026-10-22 |
| The Host turns off the expo plugin's OAuth redirect | `@better-auth/expo` mounts `/expo-authorization-proxy`, which redirects to any https site. Night Shift has no OAuth sign-in, so `disabledPaths` turns it off: the phone needs only the plugin's `expo-origin` handling. | 2026-10-22 |
| The push contract is one leaf entry of `notifications`, which the client re-exports | The notification keys, the push categories and data, and where a tap goes were copied on the Host, the client, the phone, the browser and the desktop, each with its own fallback. `@nightshift/notifications/contract` imports nothing, so `client` (layer 5) may import it and pass it on to both apps. The service worker (`apps/web/public/sw.js`) stays plain JavaScript: a test runs it against the contract, so no build step is needed. | 2026-10-22 |
| `gates.resolve` declares typed refusals, and the lock-screen rule is on the Host only | A screen guessed "closed" from any bad request, so a full run cap read as "Someone already answered". The procedure declares `GATE_CLOSED`, `NEEDS_APP`, `FORBIDDEN` and `NOT_FOUND` (oRPC `.errors`), and the engine throws `GateClosedError` for a Gate that no longer waits. The client's `answerGate` turns them into one outcome both apps show with the same words. The phone sends a lock-screen answer without reading the open Gates first: a push is no proof, so the Host checks the mark and the choice. | 2026-10-22 |
| The Device's exchange is tested in memory | `inMemoryHost` (`@nightshift/devices/testing`) is `HostClient`'s second adapter: a `HostExchange` in the same process, with the router's key rules and error mapping. The Device's real exchange (`DeviceExchange`) runs against it, so its cursors, Commands and reconnects are tested in seconds. The two-daemon tests keep one path each, to check the transport. | 2026-10-22 |

## Known Pain Points

- `@tanstack/ai` moves fast (0.39 → 0.68 in a few months). Pin exact versions and upgrade on purpose.
- Electrobun packaging needs a static web build of TanStack Start. Not yet verified.
- Not yet verified: whether the harness adapters accept our own tools, and whether they expose session resume and the usage-limit reset time.
- `drizzle-orm` is a release candidate.
- Hermes (Expo SDK 58) cannot compile a destructured rest parameter, which `@orpc/client` uses. `apps/mobile/babel.config.js` runs `@babel/plugin-transform-parameters` on the `@orpc` packages only.
- Bun's isolated installs keep several copies of one version of a package (one per set of peers). Expo's autolinking module resolution puts one copy of each in the phone's bundle, but `expo-doctor` reports the copies as duplicates. They do not break the native build: on 2026-10-21 `expo run:ios` (Xcode 27, iPhone 17 Pro simulator, iOS 26.5) built, installed and ran the app, Metro bundled it, and sign-in, the tabs and Settings worked against a sandbox Host. No fix was needed, so `check-layers` keeps its guarantees unchanged.
