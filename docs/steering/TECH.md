## Architecture

- **Pattern:** Ports and adapters. The engine depends on interfaces. Harnesses, decider providers and git (`packages/engine/src/projects/git.ts`) are adapters behind them.
- **Module structure:** A layered vertical codebase in a Bun workspace. Packages sit in layers and import only downward. Inside a package, code is grouped by domain. `docs/steering/STRUCTURE.md` holds the layer map, what each package owns, and the rules. Two scripts check them on every commit and in CI: `scripts/check-layers.ts` (the layer map) and `scripts/check-verticals.ts` (the verticals of every workspace).
- **State management:** The server stores durable facts in libsql and appends every change to an event log. The UI derives status from facts and subscribes to the event log over SSE through TanStack Query.
- **Data flow:** UI → oRPC → engine → agents (harness or tool) → facts + event → SSE → UI. Everything runs in-process.
- **API contract:** The oRPC router in `packages/api` is the one source of the API. The web client, the OpenAPI document and the agent tools all come from it. Every procedure declares an input schema, an output schema and a one-line summary. An output schema checks a reply and never changes it (`packages/api/src/output.ts`). One part of it comes from below: the peer protocol a Device calls on its Host is an oRPC contract in `packages/devices` (`hostContract`), implemented there (`hostRouter`), and mounted in that router at its paths.
- **One daemon runtime:** `packages/daemon` builds the daemon in one function (`createDaemon(env)`) and starts it in one boot sequence (`startDaemon()`). `bun run dev` (`apps/server/src/main.ts`), `nightshift serve` (`apps/server/src/features/cli/`) and the desktop app all call `startDaemon()`. Under `bun --hot` a reload calls it again: the lease, the documents and the listeners stay, and the devices runtime hands over to the next one (`startDevices`): the engine before lets go of its runs (`Engine.dispose`), and the work of placed steps goes on.
- **Devices:** `packages/devices` is this computer among other Devices and Hosts: Placement, Offers, the exchange of run history, the Links and pairing, this computer as a Host, the work relay, and the peer protocol (the Host's procedures, written once as an oRPC contract and implemented once). The engine declares the ports it needs (`Peers`, and `DeviceDirectory` for the Device rows), and `createPeerEngine` wires them. The engine never imports `devices` and never queries its tables. The daemon starts the devices with one call (`startDevices`), which builds the engine with its peers and every devices piece.
- **Notifications and the phone:** `packages/notifications` is the notifier. It reads the run log and decides whom to tell: a new Gate (keyed `runId:stepId`), a run that finished, a run that failed, a step that waits for an offline Device (keyed `runId:wait:<stepId>`, to the Person the run runs for only). The settings belong to the Person. Each channel (the in-app stream, Web Push, a desktop notification, Expo Push) sits behind a port. The phone app (`apps/mobile`) is a Person's client of a Host, not a Device. It shares its client logic with `apps/web` through `packages/client`. See `docs/research/mobile.md`.
- **Harness adapters:** `packages/agents` has one folder per harness in `src/harnesses/`: `claude-code/`, `codex/`, `opencode/`, `grok-build/`, and `acp/`. Each folder holds what is that harness's own: `facts.ts` (its entry of `HARNESS_CATALOG` in `@nightshift/flows`, plus the CLI, the take-over command and the skill folders: pure data), `record.ts` (the facts, the adapter's models and the install check), and `harness.ts` (a `HarnessSpec`, a TanStack adapter factory and a raw-message observer). The models in `record.ts` are a copy of the adapter's list, typed against it (`satisfies typeof CODEX_MODELS`), so a package update that changes the list fails the type check. The adapter factory loads its package with `import()` on the first session. The decider providers, the sandbox and the MCP SDK load the same way: importing `@nightshift/agents` loads none of them (`src/index.test.ts`). `harnesses/registry.ts` and `harnesses/facts.ts` collect one record per harness. `harnesses/facts.ts` is the browser-safe `./harness-facts` entry. `src/session/adapter-session.ts` runs every Agent step as one TanStack AI session: it owns the sandbox in the worktree, the `chat()` call, the translator, the step report and the abort. `acp/` runs every agent that speaks the Agent Client Protocol through `acpCompatible`: GitHub Copilot, Gemini CLI, Cursor, and pi (through the `pi-acp` package, which `packages/agents` ships, see `acp/pi.ts`). Night Shift finds pi-acp when a pi session starts, not when it loads. The `nightshift` binary carries pi-acp inside and starts it as `nightshift pi-acp`. An agent without a model flag gets its model over ACP (`acp/session-config.ts`). A custom agent (`acp:<slug>` in a flow, `customAgents` in the settings) runs through the same path, with the command the person gave. `HARNESS_CATALOG` (`packages/flows/src/harnesses/`) holds what a person sees of each harness: label, initials, note, default model, the models the editor suggests, where the code goes, and the setting of its CLI path. It is browser-safe, so the web app reads it too. To add a harness, add its folder, one line in `registry.ts` and in `facts.ts`, and its name and its catalog entry in `@nightshift/flows` (`harnessNameSchema`, `HARNESS_CATALOG`).
- **Flow execution:** A flow is Night Shift data, not a file in the repository: a Yjs document in the Space that keeps its Project. The Space's Host keeps it (a Space without a Host, its one Device), and every Device of the Space has a copy in its Replica ([ADR 2](../adr/0002-flows-are-night-shift-data.md)). A zod schema validates it. Every Agent node runs as a harness session through a TanStack AI harness adapter and names a skill the harness already has. A Decision node picks one of its options: you (a Gate), a rule (a JSONata expression over the run's values), or a model whose pick is checked against the options.

## Key Constraints

- Store facts, never status. Derive status in a query or a view. Append an event for every change.
- The engine owns order, retries, loop limits, and gates. A model decision is a schema-validated label. Never let a model change the graph.
- Every loop in a flow has a maximum count. The validator refuses a flow with an unbounded loop.
- Every external I/O goes behind an interface in `packages/agents` or `packages/engine`. No `gh`, `git`, or harness call outside an adapter.
- Never delete a dirty worktree. Garbage collection skips any tree with uncommitted changes.
- Cap concurrent sessions. The cap is configuration, not a constant.
- A step runs in one repo. A cross-repo change is two steps.
- Put a tenant id on every row: `space_id`, the Space (a Better Auth organization). No query of a person crosses a Space. Only background work (the walk, recovery, the scheduler) reads every Space, and it writes each row with its own Space.
- Validate every flow with the published zod schema before a run starts. A schema error stops the run.
- The app holds secrets in the OS keychain. Prefer the CLI's own login over a stored token.
- A step that runs unattended ends with a structured report. It never waits on a person mid-session.
- No PTY. A session is a structured event stream.

```bash
# Apply the schema to the dev database (.nightshift-dev/)

# Dev (web + server, hot reload)
bun run dev

# Dev desktop shell

# Run tests
bun test

# Lint + format
bun run check

# Type-check

bun scripts/check-layers.ts

# Build (desktop last)
bun run build

# Git hooks
bun lefthook install
```

## Code Conventions

- **Naming:** PascalCase components and types, camelCase functions and variables, kebab-case file names.
- **File structure:** One workspace package per bounded context. Inside a package, group by feature, not by kind. Each vertical is a folder with an `index.ts` barrel as its only public surface (`src/features/<vertical>/` in apps, `src/<vertical>/` in packages). No `lib/`, `utils/` or `hooks/` buckets at the top of `src/`. See `docs/steering/STRUCTURE.md`.
- **Test files:** Colocated `*.test.ts` next to the module. Bun's test runner.
- **Imports:** Workspace packages by name (`@nightshift/db`). No relative imports across packages.
- **Formatting:** Biome. The pre-commit hook formats staged files.
- **Environment:** varlock schemas in `.env.schema`. Generated types, never `process.env` by hand.
- **Prose:** Durable docs follow the ASD-STE100 style of the WTF skills. Short sentences, active voice, one idea per sentence.

## Known Pain Points

- `@tanstack/ai` moves fast (0.39 → 0.68 in a few months). Pin exact versions and upgrade on purpose.
- Electrobun packaging needs a static web build of TanStack Start. Not yet verified.
- Not yet verified: whether the harness adapters accept our own tools, and whether they expose session resume and the usage-limit reset time.
- `drizzle-orm` is a release candidate.
- Hermes (Expo SDK 58) cannot compile a destructured rest parameter, which `@orpc/client` uses. `apps/mobile/babel.config.js` runs `@babel/plugin-transform-parameters` on the `@orpc` packages only.
- Bun's isolated installs keep several copies of one version of a package (one per set of peers). Expo's autolinking module resolution puts one copy of each in the phone's bundle, but `expo-doctor` reports the copies as duplicates. They do not break the native build: on 2026-10-21 `expo run:ios` (Xcode 27, iPhone 17 Pro simulator, iOS 26.5) built, installed and ran the app, Metro bundled it, and sign-in, the tabs and Settings worked against a sandbox Host. No fix was needed, so `check-layers` keeps its guarantees unchanged.
